# Protocol fixtures

These small JSONL files are versioned examples of the app-server messages consumed by the prototype. Request and response lines use the same JSON-RPC ID; notification fixtures have no ID. Unknown response fields are intentional and verify forward-compatible parsing.

When the supported wire protocol changes, update the smallest relevant fixture and its assertions in `src/fixture-tests.ts` together. Keep fixtures representative, redacted, and independent of local thread IDs, authentication, or conversation content. `thread-resume.jsonl` records the verified continuation handshake: `thread/read` reads history, while `thread/resume` activates an existing thread before `turn/start`; `thread-resume-read-only.jsonl` records a thread that must not accept direct input. `process-exit.jsonl` and `timeout.jsonl` describe transport scenarios rather than server messages; the fake app-server integration tests exercise the actual process exit and no-response behavior.

`thread-active-writer.jsonl` records the guarded case where the server reports an active turn. The desktop service must classify it as a busy thread and must not issue `turn/start`; there is currently no verified per-turn cancellation method in this protocol set.

`thread-fork.jsonl` records the fork request, inclusive `lastTurnId` cutoff, source/session metadata, and subsequent read/list hydration. The fields were checked against bindings generated by local Codex CLI `0.162.0-alpha.17.2` on 2026-10-12; these redacted examples are not complete captured user sessions. `thread-fork-active-turn.jsonl` represents the documented invalid-parameter case for an in-progress cutoff. Actual process, cutoff, mutation isolation, restart, missing-capability and failure behavior is tested by the dedicated stateful `fake-fork-app-server.ts` fixture, not inferred from these JSONL examples.

## Terminal status and history loading fixtures

`terminal-statuses.jsonl` covers explicit completed/failed/interrupted outcomes and unknown/missing statuses. Unknown or missing statuses must settle as client compatibility failures, never success. The existing successful completion fixtures now include `status: "completed"`; missing status is deliberately covered by the negative fixture.

`history-items-view.jsonl` covers both thread/read and thread/turns/list projections of notLoaded, summary, full, an empty full body, and an older response without itemsView. These are synthetic schema-based cases. Desktop pagination tests additionally cover full/summary priority, overlapping pages, route switches, paginated metadata-only reads, stable navigation and virtual list offsets without additional RPCs.

The M6-B regression sequences additionally cover repeated missing user echoes followed by a real echo, equal-text user IDs and turns, pagination echo reconciliation, shorter/empty replacement full bodies, new summary item IDs, and out-of-order reads/pages. Terminal service tests cover unknown/missing history after notifications and route switches, explicit terminal resolution with notLoaded bodies, and terminals arriving before the turn/start response. Fake desktop E2E also rereads unknown/missing terminal history and verifies that it stays non-final with a distinct compatibility label.

## Token Usage fixtures

`token-usage.jsonl` contains synthetic `thread/tokenUsage/updated` examples: a valid snapshot, its duplicate, an explicit null window, a malformed breakdown and a resume request/response followed by replay of the original snapshot. Replay is an absolute replacement, never additional usage. The fields mirror `artifacts/codex-schema/ts/v2/{TokenUsageBreakdown,ThreadTokenUsage,ThreadTokenUsageUpdatedNotification}.ts`; no real conversation content is included.
